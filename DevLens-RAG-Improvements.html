Making the code chat answer whole-project questions

Why the RAG pipeline in devlens-ai could only answer narrow lookups, what was changed in ingestion and retrieval, and how to verify it.

The fixIndex the repo at three levels (repo, file, code), route each question to the right level, and combine vector and keyword search.

1. Why the old pipeline failed

The original flow was: clone the repo, extract functions with tree-sitter, embed each function with Jina, store it in pgvector, then answer a question by embedding it and pulling the 8 most similar functions. That works for “where is save_chunks defined?” but breaks for anything broader. Four separate causes stacked on top of each other.

Root cause 1Nothing in the index described the whole project

Only function and method bodies were stored. A question like “how can I improve this project?” has no close match among individual functions, so the top 8 results were effectively random, and the model had no picture of the architecture, tech stack or file layout to reason about.

Root cause 2Large parts of the code were never indexed

For supported languages, a file with no function matches returned zero chunks. Enums (enums/Status.py), the fields of Pydantic models (models/requests.py), most of the settings class in config.py, class declarations, imports and top-level wiring such as router registration in main.py were all invisible to search. Python decorators like @router.post("/chat") were also cut off from their functions.

Root cause 3Follow-up questions were searched without their history

Only the latest message was embedded. “What changes do I need to make?” means nothing on its own; the subject (“the ingestion pipeline”) lives in the previous turn. The history was passed to the answering model but not to the search.

Root cause 4The prompt forbade recommendations

The system prompt said to answer using only the context and otherwise reply “I couldn’t find that in the indexed codebase.” An improvement question needs engineering judgement applied to the code, which that rule ruled out even when the right code was retrieved.

Two weaker spots made specific questions less reliable too: pure vector search is poor at exact identifiers like updateFilesProcessed, and there was no reranking step to put the best of the candidates first.

2. The approach

The fix gives the index three levels of detail and teaches the query side to pick the right level for each question.

LevelWhat is storedAnswers questions like
RepoOne LLM-written overview per repo (purpose, tech stack, architecture, key files, weak spots) plus the file tree. Table repo_overview.“What does this project do?”, “How can I improve it?”
FileOne summary chunk per file: imports and the signatures of every class and function. chunk_type = 'file_summary'.“Which part handles auth?”, “How is the backend structured?”
CodeFunctions, methods, class headers and top-level module code, each with file path and line range.“Where is X called?”, “Why does Y fail?”

3. Ingestion changes

File: services/pipeline.py, new services/overview.py.

1. CloneWorking copy in tmp/
2. WalkFilter by extension, size, binary
3. Clear old indexDelete the repo’s chunks and overview
4. Chunk + summarizeCode chunks and one file summary per file
5. Embed + save in batches200 chunks at a time
6. Repo overviewOne LLM call, stored in repo_overview

Before

  • Re-ingesting a repo inserted a second copy of every chunk.
  • All chunks and embeddings were held in memory until the very end.
  • No file-level or repo-level information.
  • Embedded text was the raw code only.

After

  • Old chunks are deleted first, so re-ingesting replaces the index.
  • Chunks are embedded and saved every 200, keeping memory flat.
  • File summaries and a repo overview are built every time.
  • Embedded text is prefixed with File: <path> and Type: <chunk_type>, so the vector knows where the code lives.

File summaries cost nothing

Summaries are built from the chunks already extracted, with no LLM call. That matters because Groq’s free tier allows only a few thousand tokens per minute; an LLM summary per file would make ingesting a 200-file repo take most of an hour. Example output:

File summary: services/rag.py
Language: py | Lines: 184
Imports / dependencies:
import json
from langchain_groq import ChatGroq
from db.pgvector import similarity_search, keyword_search, get_repo_overview
Defines:
- [function] def create_llm(groq_key: str, model: str, streaming: bool = True) -> ChatGroq: (line 44)
- [function] async def route_question(question: str, history: list[dict], groq_key: str) -> dict: (line 58)
- [function] async def hybrid_search(...) (line 98)

The repo overview

One call to the overview model gets the file tree, README, dependency manifests (requirements.txt, pom.xml, package.json, Dockerfile and so on, at the root and one level down) and as many file summaries as fit in about 24,000 characters. It returns Markdown with fixed sections: Purpose, Tech stack, Architecture & data flow, Key files, Weak spots & improvement opportunities. If the LLM call fails, the raw material is stored instead, which is still far more useful for broad questions than nothing.

4. Chunker changes

File: services/chunker.py. The existing structure and naming were kept.

ChangeWhy
Capture classes, interfaces, enums, structs and traits for every supported languageType definitions, fields and Pydantic/Spring model shapes were missing from the index.
Class chunks hold only the header (decorators, fields, signature) up to the first method, capped at 80 linesMethods already get their own chunks; storing the whole class would duplicate them.
New module chunks for lines outside every function and classImports, constants, app and router wiring are now searchable.
Include Python decorators with their function@router.post("/chat") is how you find an endpoint.
Skip functions nested inside other functionsThe parent chunk already contains them.
Split functions longer than 150 lines into 120-line windows with 20 lines of overlapKeeps chunks focused and within the embedding model’s input limit.
Fall back to sliding windows when a parsed file yields nothingNo supported file is silently dropped.
Added .jsx and .tsx parsingThe React frontend previously got only generic 60-line windows.
Paths stored with forward slashesConsistent citations whether ingestion runs on Windows or Linux.
Crash fix. Reading node.end_point in tree-sitter 0.26 on Python 3.14 intermittently causes an access violation that kills the process. The original chunker used it too, so ingestion could die partway through a repo. Line numbers are now computed from byte offsets using a precomputed list of newline positions and bisect, which avoids that call entirely and gives identical results.

5. Retrieval changes

Files: services/rag.py, db/pgvector.py, services/embedder.py.

1. RouteRewrite with history, label scope, pick keywords
2. EmbedRewritten question + keywords
3. RetrieveDifferent context per scope
4. Fuse + rerankVector + keyword, then Jina reranker
5. AnswerStreamed from the chat model

Step 1: question routing

A small, fast model (openai/gpt-oss-20b) receives the last six messages and the new question, and returns JSON:

{"query": "What changes do I need to make to the ingestion pipeline?",
 "scope": "global",
 "keywords": ["ingestion pipeline", "tree-sitter", "Jina", "pgvector"]}

That is real output from testing: the follow-up “what changes i need to do?” was resolved using the earlier turn about ingestion. If the router call fails, a keyword list (improve, refactor, architecture, overview, security and similar) decides the scope and the original question is used as-is. Questions that match those keywords are always treated as global, even if the router says otherwise.

Step 3: what each scope retrieves

globalProject-level questions

  1. Repo overview
  2. File tree (up to 6,000 characters)
  3. 12 most relevant file summaries
  4. 6 code chunks from hybrid search

specificTargeted questions

  1. 10 code chunks from hybrid search
  2. 3 related file summaries for orientation

Step 4: hybrid search and reranking

Vector search finds code that means the same thing; keyword search finds code that contains the exact identifier. Each returns 30 candidates, which are merged with reciprocal rank fusion (each list contributes 1 / (60 + rank) to a chunk’s score). The merged top 30 are then reranked by jina-reranker-v2-base-multilingual using the existing Jina key. If the reranker is unavailable, the fused order is used.

Keyword search uses a generated Postgres tsvector column over the file path and content, with a GIN index. Questions are reduced to identifier-like tokens joined with OR, with common words removed; underscores are split the same way Postgres splits them, so save_chunks matches.

"where is updateFilesProcessed called and how does save_chunks work"
  →  updatefilesprocessed | called | save | chunks

6. Prompt changes

Before

  • Answer using only the context.
  • Otherwise say exactly “I couldn’t find that”.
  • No guidance for design or improvement questions.

After

  • Every factual claim about the code must come from the context, with file and line citations.
  • For improvement, design, security and performance questions, give prioritized recommendations, tie each one to specific files, and show short code examples.
  • “I couldn’t find that” is only for factual questions with no support, and should mention the closest thing found.

Chat history sent to the model is now capped (10 messages by default), and failures during retrieval or streaming return a short message instead of breaking the HTTP stream.

8. Configuration

New settings in app.properties, with matching defaults in config.py:

devlens.app.llm.chat_model=openai/gpt-oss-120b
devlens.app.llm.router_model=openai/gpt-oss-20b
devlens.app.llm.overview_model=openai/gpt-oss-120b
devlens.app.rag.rerank_enabled=true
devlens.app.rag.max_history_messages=10

The router was first set to llama-3.1-8b-instant, but that model is not available on the project’s Groq account, so it uses openai/gpt-oss-20b, the small model the account does have.

10. Next steps

  1. Re-ingest every connected repo. Existing indexes have no file summaries or overview, so global questions will fall back to code chunks only.
  2. Smoke-test these questions on a freshly indexed repo:
    • “What does this project do?”
    • “How can I improve this project?” then “What changes do I need to make?”
    • “Where is updateFilesProcessed called?”
  3. Known remaining bug: when MongoDB is disabled, mongo_db is None and the status updates in db/mongo.py will fail, which stops ingestion.
  4. Possible later improvements: an atomic swap instead of delete-then-insert (so a repo stays searchable during re-indexing), and a small evaluation set of question/expected-file pairs to measure retrieval quality over time.
